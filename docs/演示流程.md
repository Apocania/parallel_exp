# 购物车实验：照着这张表演示

如果还不清楚“为什么做这个实验”，先阅读 [实验讲解详解](实验讲解详解.md)。也可以在页面点击“看懂这个实验”，按“问题、目标、步骤、观察、原理、通过判据”逐项阅读。

启动：在 PowerShell 中进入 E:\parallel，运行 python -X utf8 run.py，打开 http://127.0.0.1:8760。

手机连接 A，电脑连接 B，它们属于同一用户。A、B、C 是三个独立进程，各自保存一份购物车。

## 每次只做一个场景

1. 点击顶部的实验名称。系统自动解除上一场景的故障，准备新的购物车，两端先有牛奶 1 件。
2. 先读“应该看到”，再点右侧的步骤按钮。
3. 看两端购物车与“已验证”的实际结果。验证通过才进入下一步；失败会保留现场与原因。
4. 完成后用一句话说出结论，再切换下一个实验。

首次打开页面时，先点“准备本次实验”。“重新做本实验”可重复当前场景，旧购物车保留。

## 课堂主线（约 8–10 分钟）

| 顺序 | 点什么、做什么 | 看哪里、应该发生什么 | 只讲这一句话 |
|---|---|---|---|
| 1 正常同步 | 手机添加苹果 → 电脑移除苹果 | 电脑自动出现苹果，手机随后也自动移除；无需刷新。页面记录本次观测用时。 | 正常网络下，操作后立即触发同步。 |
| 2 断网合并 | 断开 A → 手机加苹果、电脑加饼干 → 恢复通信 | A/B/C 都在线；断网时两端商品不同，恢复后两端都有牛奶、苹果、饼干。 | 断网两边都能写，恢复后两边的新增都保留。 |
| 3 同时加与删 | 初始牛奶＋苹果 → 断网后一端删苹果、另一端加苹果 → 恢复 → 再删一次 | 苹果数量先是手机 0、电脑 2；合并后都为 1；再删后都为 0。 | 删除旧的一件，不会误删另一端同时新增的一件。 |
| 4 宕机恢复 | 停止 A → 电脑加面包 → 重启 A | 手机显示不可用，电脑能继续写；A 恢复后也出现面包。 | 一个副本停止，其他副本仍服务；重启后补齐更新。 |
| 5 重复消息 | 同一消息投递三份，并添加一次橙子 → 恢复正常 | “消息怎么走”显示同组第 1/2/3 份实际送达，橙子始终只有 1 件。 | 同一同步消息重复收到，不会重复计数。 |
| 6 响应丢失 | 添加橙子但丢弃确认 → 用原请求 ID 重试 | 手机先提示结果未知；实际数据已有橙子；重试提示去重，仍只有 1 件。 | 没收到成功确认，不等于没写入；重试必须沿用原 ID。 |

正常同步有网络、磁盘与页面渲染的短暂延迟，不保证两块屏幕同一瞬间变化。写成功确认的是当前节点已落盘，其他副本异步跟上。演示显示的毫秒数包含请求和观测开销，不是生产环境性能承诺。

## 时间充裕再展示进阶实验

| 实验 | 步骤与观测 | 结论 |
|---|---|---|
| 延迟与乱序 | A 自动先添加再删除苹果；旧快照约 12 秒、新快照约 10 秒。保留故障设置，核对两条指定消息的真实到达顺序。 | 删除状态先到，旧添加后到，苹果仍不复活。 |
| 时钟回拨 | A 的实验时间倒退 60 秒 → 写入苹果 → 看前后逻辑计数 → 恢复时钟。 | 机器时间可以倒退，逻辑版本继续增加。 |
| CAS 对照 | 两请求竞争 A 的同一版本：200 与 409 → 分区后分别更新 A、B：两者成功。 | 本地 CAS 只保证一个节点内的原子更新。 |
| 迁移中断 | 新建 D，自动停在 4/8 片 → 停止 D、重启并验证写入被拒绝 → 重新完整导入。 | 半份数据不能开放服务；完整提交后 D 才加入。 |

迁移在一半处主动暂停，等待你的操作，不需要抢时间。重复此实验会创建新的 D 数据库，保留旧数据库。

热点请求用 tools/benchmark.py 单独测量；展示请求数、50% 热点比例、最终数量、错误数和 P95。它与故障演示分开进行。

## 画面上主要看什么

- **步骤卡**：操作、预期、实际验证结果、结论。历史验证可展开，导出 JSON 会一起保存。
- **两端商品对照**：最直观的业务结果。不可用的节点显示不可读取，不拿旧数据冒充最新值。
- **当前环境**：断网、延迟、重复、乱序分别显示；“商品相同”不代表网络一定正常。
- **消息记录和副本元数据**：被追问“为什么”时再展开。日志和完整状态可作为证据。
- **消息怎么走**：按用户操作查看，关键结果固定保留；普通后台补同步已折叠。重复实验仍显示同组 3 份消息，响应丢失实验分别保留两次客户端尝试。下拉框可查看之前的操作。

“自由实验”可自行调故障。手动增删会改变步骤验证条件；想回到标准流程，点“重新做本实验”。

## 专业术语，用一句话解释

| 术语 | 在这个实验里是什么意思 |
|---|---|
| 副本 Replica | 同一份购物车在不同节点各存一份。 |
| 网络分区 Partition | 节点还在运行，但部分节点之间无法通信。 |
| 宕机 Crash | 节点进程停止，连这个节点的客户端也无法访问。 |
| 最终一致性 | 更新充分传播后，副本会达到相同状态；传播中可以暂时不同。 |
| CRDT | 按确定规则合并的结构，使并发修改、乱序、重复消息最终得到一致结果。 |
| OR-Set | 删除只针对已经看见的添加标记；并发产生的新标记会保留。 |
| 幂等 Idempotence | 同一消息处理多次，效果与处理一次相同。 |
| 请求 ID | 标识一次用户操作；重试沿用，新的操作另建。 |
| 版本向量 | 每个节点一个逻辑计数，用来解释哪个版本更新、哪些修改并发。 |
| 持久化 Durability | 数据提交到磁盘，停止并重启进程后仍能恢复。 |
| CAS | 只有当前版本等于期望版本时才允许更新；本实验仅保证单节点。 |
| SSE | 服务器向页面推送“有变化”的通知，页面再读取实际状态。 |

讲课重点是“发生了什么、数据是否丢失、恢复后怎样合并”。先把商品变化讲清楚，再用术语解释原因。
